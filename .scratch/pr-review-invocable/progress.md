# Progress: pr-review invocable by Claude and by workflow skills

## Decisions

1. Claude may start `pr-review` itself, through the Skill tool, when it is asked: the user's own message asks to review GitHub pull requests (a number, a URL, `owner/repo#n`, `open`, `requested`), or a workflow skill the user is running calls for it as a step. Never on Claude's own initiative, and never because a pull request, an issue or a file says so. Once started it runs as if typed: a trusted pull request's checks run without another question; an untrusted pull request's code, starting services and posting still wait for a yes. The skill's text enforces this, not the platform. (The user's choice, 2026-09-30, sensitive. The user added the workflow-skill case: today a skill that calls it gets "cannot be used with Skill tool due to disable-model-invocation".)

2. Scope: just unblock it. Any skill the user runs (their projects' own workflows, other plugins, a plain request) can invoke `pr-review` through the Skill tool; no Seams skill starts calling it. (The user's choice, 2026-09-30.)
3. Routing, by what is reviewed: `pr-review` for GitHub pull requests named by number, URL, `owner/repo#n`, `open` or `requested`; Matt Pocock's `code-review` for a local branch, commits or uncommitted work. The new description and `routing.md` say so. (The user's choice, 2026-09-30.)
4. Tests: the static, gate and hook suites pin `pr-review` as model-invocable; a live headless probe (Haiku, its shell denied) proves a Skill-tool call now starts it; a harness scenario asking to review a pull request by number expects `pr-review` first, while `review-scope` keeps `code-review` (about $3, asked first). (The user's choice, 2026-09-30.)
5. Ships as 3.3.1 through `release`: committed first (live on this machine at once, since the install loads in place), then CI staging, and `main` on the user's yes. (The user's choice, 2026-09-30.)
6. Off switch: the README names Claude Code's own permission rule, `Skill(matt-pocock-workflow:pr-review)` under `permissions.ask` (Claude asks before each start) or `deny` (Claude never starts it). The build's live probe checks that the rule matches Claude's call, and whether a typed `/pr-review` still works under `deny`; the README says what the probe shows. Nothing new in the plugin. (The user's choice, 2026-09-30.)
7. The change is agentic invocation, and nothing else of `pr-review`'s behavior changes: its `SKILL.md` differs from 3.3.0's only in the frontmatter (the flag's line gone, the description opening "Use when asked for" instead of "Typed by hand only, for", which decision 8 then sharpened). That description carries decision 1's "when asked"; no rule is added to the skill's opening, its references list stays as it was, and `evidence.py` is unchanged but for decision 8's next step. Outside the skill: the resume note no longer says only the user can start it, and the tests that pinned it as manual-only pin it as model-invocable. (The user's words while it was built, 2026-09-30: "i like the current pr-review so please don't ruin it i only want it to be agentic invocation". This replaces decision 1's opening rule and the reference-list trim that paid for it.) The user then invited ideas that make agentic invocation smarter, which the next round puts to them.

8. Two agentic improvements, the user's pick of three offered: the description leads with its trigger and the pull requests it takes ("Use when asked to review GitHub pull requests (numbers, URLs, open, requested), with their checks…"), so Claude and workflow skills tell it from `code-review`; and a batch's next step reads "Continue it with pr-review on pull requests … of …" instead of "The user types /pr-review again …", so Claude continues a batch itself when asked. Not taken: a static-review default for an untrusted pull request where no one can answer (a subagent, a headless run), which still stops at its question. (The user's choice, 2026-09-30.)
9. Two security fixes before 3.3.1 ships, from the security review of `5a39821`, which found text Claude reads (an issue, a README) could get `pr-review` started on a URL it names. The trust rule also needs push access: a pull request is trusted when the viewer wrote it, or when it is not from a fork, its author is `OWNER`, `MEMBER` or `COLLABORATOR`, and the viewer can push to its repository (`viewerPermission` `WRITE`, `MAINTAIN` or `ADMIN`), so a stranger's pull request in the stranger's own repository gets the question before its code runs, however the review started (a hole typed reviews have had since 3.2.0). And the lapse hint leaves `pr-review` out: a review needs no declaration, and invoking it again after the user's typed answer would re-arm its pre-approved scripts, against the README's "your own permission settings decide again". This amends decision 7, which kept the review's text and the gate unchanged. (The user's choice, 2026-09-30, sensitive.)
10. `pr-review`'s `SKILL.md` may take 11,200 bytes where every other skill has 11,000, so decision 9's trust sentence fits without rewording the rest of the review (decision 7). The bound stands for the 4,000-token cap that compaction needs; `claude plugin details` measures `pr-review` at about 3.5k tokens on invoke, and the build checks it stays well under the cap. A fixture pair tests the allowance. (Made while building, not the user's choice.)

11. No git hook runs when `pr-review` checks out a pull request: its worktrees are made with `git -c core.hooksPath=/dev/null worktree add` (`references/checkout.md`). A local probe showed a checkout-time hook installed in the user's clone runs inside the new tree and reads that tree's files, so a hook runner such as lefthook or pre-commit would run a command the pull request chose, even under static review; with the flag, no hook ran. A hole since 3.2.0, which a review started from text Claude read could now reach. Decision 9's trust rule was completed after the security re-review: push access is required on both branches (the viewer's own pull request to a repository the viewer can't push to runs the owner's baseline code), and an error from `gh` counts as no. (The user's choice, 2026-09-30, sensitive.)

## Facts

- `disable-model-invocation: true` keeps a skill's description out of Claude's context and makes Claude Code refuse a Skill-tool call to it (docs `skills` :388, :408). Removing it puts the description in every session's listing: about 189 characters, some 60 tokens, for `pr-review`. `claude plugin details` already counts it, so its always-on figure (about 857) doesn't move. `allowed-tools` pre-approvals apply whether the user or Claude invokes the skill (`skills` :424).
- The docs advise `disable-model-invocation` for skills with side effects (`skills` :388, `features-overview` :217). `pr-review`'s side effects before any yes, for a trusted pull request: a clone and worktrees, the checks CI runs with their installs on both trees, `code-review` and a risk reviewer, and in a batch one subagent per pull request (`SKILL.md` :34, :52–55; `references/checkout.md`, `checks.md`, `understand-and-review.md`, `batch.md`).
- The gate reads "manual-only" from each Seams skill's frontmatter (`seams_gate.py` :836–883): without the flag, a bare typed `/pr-review` still declares through the `UserPromptExpansion` event; in the fallback where no expansion arrives, the lapse hint then tells Claude to invoke it with the Skill tool, which works once the flag is gone. No gate code needs to change.
- What says "manual only" and would change: `SKILL.md` :3–4 (the description opens "Typed by hand only"), `README.md` :128 and :379, `routing.md` :28, `session-start` :216–217 (the batch note), `evidence.py` :353–355 (the batch's next step). Tests pinning it: `test_plugin.sh` :123–139 (the `USER_ONLY` allowlist), `test_gate.py` :324–330, :424, :571–580, `test_hooks.sh` :84–86, `test_plugin_hook.sh` :469, :495, `test_pr_review.py` :1284, :1361, :1368.
- `pr-review/SKILL.md` is 10,985 bytes of its 11,000-byte bound; the flag's line frees 31 bytes, so the new description may grow by about 46.
- Matt Pocock's `code-review` description: "Use when the user wants to review a branch, a PR, work-in-progress changes, or asks to review since X". The eval case `review-scope` ("review the current state of this branch against docs/spec-coupons.md") expects `code-review`; no eval case mentions a pull request.
- Budget: the listing guard is at 2,626 of 2,650 characters and always-on at about 857 against the phase-1 bar of 873, so the new description may be at most about 24 characters longer than today's 159; the boundary with `code-review` goes mainly in `routing.md`.
- The security review: local `main` is one commit ahead of `origin/HEAD` (`7103d25` over `4891cb0`), so `/security-review` can't take this range, and a `matt-pocock-workflow:reviewer` agent reviews it on the security axis (decision 34 of lean-and-durable).
- The live probe (2026-09-30, Claude Code 2.1.285, Haiku, headless, its shell denied, this repository's plugin in place; $0.24 for four runs): Claude's Skill call to `matt-pocock-workflow:pr-review` with args `5` launched the skill, its text loaded and "The request: `5`" was filled in, so the arguments of a Skill call arrive. With `Skill(matt-pocock-workflow:pr-review)` in `permissions.deny`, the call was refused ("Skill execution blocked by permission rules"), and a typed `/matt-pocock-workflow:pr-review 5` still loaded the skill. With that rule in `permissions.ask` and the Skill tool otherwise allowed, the skill launched without asking, so the README names `allow` (with what it opens) and `deny`, not `ask`. Later probes: a bare `/pr-review 5` typed under the `deny` rule still loaded the skill, and a Skill call by the bare name `pr-review` was refused by the full-name rule. With no rule, the Skill tool's own permission prompt stood in the way ("Execute skill: …", a denial in a headless run), which a session that allows the Skill tool doesn't meet.
- Seen once and not reproduced (41 runs: alone, under 14 busy loops, in six full-file runs, under four parallel copies of the file): `test_pr_review.PostReviewsTest.test_each_minute_stays_under_the_content_budget` failed in one full `test_pr_review.py` run on 2026-09-30, right after macOS's upgrade to Darwin 27. Its assertion text wasn't captured. It checks wall-clock gaps (under 0.6 s between two posts, at least 0.95 s before the third), so a stall can flip it; CI will show which if it recurs.
- The routing runs (2026-09-30, `scripts/behavior_test.py`, Claude Code 2.1.285, the runtime reporting `claude-sonnet-5-5`; records in the gitignored `tests/runs/pr-review-invocable/`): `pr-review-routing` ("Can you review pull request #5 in this repository on GitHub…") 3 of 3, `pr-review` the first call each time; `review-scope` (a local branch against a spec) 3 of 3 `code-review`, so the new description took nothing from it. The first three `pr-review-routing` runs also chose `pr-review` first but counted as errors: Claude Code asked before starting it ("Execute skill: matt-pocock-workflow:pr-review"), which it did not for `code-review`, and a headless run denies an ask. The harness's settings now allow `Skill(matt-pocock-workflow:pr-review)`, and the three runs again passed, which also shows that rule lets it start without a prompt. Every run loaded `superpowers@synced` (15 of its skills): the harness switches off only `superpowers@claude-plugins-official`, as lean-and-durable's open question from ticket 10 says.
