## Decisions

1. `pr-review` posts its review to GitHub without asking, for all three events (comment, request changes, approve), whenever the review is fully verified at the pull request's current head. Fully verified means: every check ran on both trees (none "could not run"), every finding is verified at the head and every blocking finding is proven, nothing is left under "not verified", and the head is unchanged at the moment of posting. Anything less drafts and asks, as today. (The user's choice, 2026-10-01, sensitive: it reverses 3.2.0's "nothing reaches GitHub without a yes", and an approval posts in the user's name with nobody reading it first. The recommended option kept approve asking; the user chose approve too.)
2. The user also wants semantic GitHub labels added: see decision 8.

3. A head that moves during or after the review is reviewed again automatically, at most twice, then the review stops and tells the user. A review is never posted against a head it did not verify. Every check re-runs on the new head; only the baseline is reused, since its commit is unchanged. (The user's choice, 2026-10-01. The option text said a new head re-runs checks "only where the changed files affect them"; that cannot be proven safe, so it was corrected to this before building.)
4. Speed and cost: only provable waste may be cut (work done twice, work that can run at the same time, context read twice, mechanical steps on a smaller model). The user did not allow skipping the baseline when the head passes, nor fewer reviewers on small pull requests. Fixed whatever is cut: `pr-review` is run on a fixed set of pull requests with planted defects before and after, and no finding or verdict may be lost; each paid run is asked first. (The user's choice, 2026-10-01.)
5. What is slow is a review's checks, in a batch: the user's example, from a private client repository, is twelve reviews run in waves, the first six taking 15 to 20 minutes because each runs the full suite and then two Postgres suites, the queued six waiting for slots, and the user holding the next wave back to stay under a 2-hour limit. Seams' own suite is not the complaint. (The user's words, 2026-10-01.)
6. A take-over's fixes go on the author's branch when GitHub lets the user push there (`maintainerCanModify` on a fork, or the same repository with access), else on a new branch and pull request of the user's that names theirs. Never a force push; a `Co-authored-by:` trailer for the author; a question naming the branch and the commit before any push. (The user's choice, 2026-10-01.)
7. Auto-post applies in repositories the user can push to (the check that already decides trust), where reviews are expected; elsewhere a fully verified review still asks first. `draft only` in the request turns it off anywhere. (The user's choice, 2026-10-01.)
8. The semantic labels are review-state labels in a prefix of their own: `pr-review: approved`, `pr-review: changes requested` or `pr-review: commented`. One per pull request, created once per repository if missing, replaced whenever a newer review posts on a new head, applied only together with a posted review, and never touching the repository's own labels, so no bot wired to a label like "ready to merge" or "automerge" fires. (The user's choice, 2026-10-01.)
9. A check's two trees run at the same time, except a check that needs a database or another service, which stays one after the other so the two runs cannot collide on it. A slot counts both trees' load. (The user's choice, 2026-10-01.)
10. A baseline result is reused within a batch: pull requests with the same baseline commit share one baseline run, the first run's result, and a failing baseline is run once more before it is trusted. Nothing is kept after the batch. (The user's choice, 2026-10-01.)
11. The user's 2-hour limit is a tool or session timeout: something ends a long review or its background run after about two hours. So a batch's total wall-clock is what has to shrink, which decisions 9 and 10 do directly; which timeout it is stays unconfirmed. (The user's answer, 2026-10-01.)
12. The take-over: after a review that is not ready to merge, the skill asks "Short on time? Take this PR over?". On yes it fixes the findings in a worktree at the head (each failing probe becomes the regression test), re-runs the checks, shows the diff, and pushes only on the user's yes, to the place decision 6 names. Merging stays the user's. (The user's choice, 2026-10-01.)

13. Tests: the poster's eligibility rule as a table of every way a review is not fully verified; the check runner (both trees at once, a service check kept serial, baseline sharing, slots counting both trees); label writes through the poster against the fake `gh`; the take-over's push target as a function; static pins for the prose; and live, a before/after on the planted-defect pull requests (#5, #6 and #7 here) and one throwaway pull request for auto-post and labels, each paid or posting run asked first. "Fully verified" is enforced by code: the poster refuses to auto-post unless the evidence on disk meets the definition. (The user's choice, 2026-10-01.)
14. `pr-review`'s core stays under its bound by moving the Post and handover detail into references read at their step; the core keeps every heading, the changed standing rule and pointers. Behavior is unchanged, and the core ends up smaller. (The user's choice, 2026-10-01.)
15. Ships as 3.4.0, a minor version for new capabilities; the roadmap's phase 2 becomes 3.5. The CHANGELOG says plainly that a fully verified review now posts by itself in repositories the user can push to, where 3.3.1 asked every time. (The user's choice, 2026-10-01; the CHANGELOG line is mine.)
16. Design points from the lens, not asked because the code or an earlier answer settles them: a label failure never blocks or undoes a posted review and the handover says so; the handover reports each review auto-posted (its URL, event and label) and each one not, with the reasons the eligibility rule gave; `posted.json` records that the post was automatic and on what evidence; a take-over of an untrusted pull request re-runs its checks only if the trust question allows it; auto-post needs the poster's script to run, and a script run in a later turn is under the user's own permission settings (a prompt, or in a headless run a draft left in `$EVID`, as today); a label stays until the next review replaces it, so after an author's push it describes the earlier head, which the README says. An ADR, 0004, records the reversal of 3.2.0's rule.
17. The reference for what a pull request must do, the user's idea (2026-10-02): the sources are a path or URL given in the request (a file, or a GitHub issue URL), and a Seams ticket or spec under `.scratch/` found automatically from the pull request's branch (`<feature>/<NN>-<slug>`) or its commit messages. A reference file inside the pull request's own branch is read from the baseline, never the head, so a pull request cannot edit its own acceptance. (The user's choice; the baseline rule is mine, to be confirmed.)
18. Precedence: the reference, then a linked issue, then the pull request's body, which is the author's own claim. Any disagreement is a finding, and a body that claims more or less than the reference is itself one. (The user's choice, 2026-10-02.)
19. With no reference beyond the pull request's own description: interactively, ask once for a ticket, a path or "go ahead"; in a batch or a headless run, go ahead and record "no independent spec: intent is the author's own description" in the review's `intent` field and its summary, not under not verified, so it does not by itself stop a comment or a request for changes from auto-posting. (The user's choice, 2026-10-02; where it is recorded is mine, to keep decisions 1 and 21 consistent.)
20. A reference is used as a requirements checklist: each acceptance criterion and each "must not happen" becomes a line the review verifies one by one and records in `review.json` (met, unmet or not verified, with its evidence); an unmet line is a blocking finding; the reference's "How to verify" commands run as checks when trust allows. "Fully verified" then needs every line met or marked not applicable. Only the Spec axis and the main session see the reference; the risk reviewer stays facts-only. (The user's choice, 2026-10-02; the reviewer rule follows the standing "facts only" rule.)
21. An approval auto-posts only with an independent reference (decision 17's sources, or a linked issue with acceptance criteria) whose every requirement line is met or not applicable. With only the pull request's own description, APPROVE asks first; comments and requests for changes still auto-post when fully verified. (The user's choice, 2026-10-02; it narrows decision 1.)
22. Design points from the lens, not asked because an earlier answer settles them: the poster's eligibility rule also checks that every requirement line the reference holds has a status in `review.json`, extracted by a script from the reference's checkboxes and "must not happen" items so coverage does not rest on the model; a posted review cites a requirement by its number and short title and never pastes a reference's text or its local path (a private ticket must not leak into a public pull request); a URL reference must be a GitHub issue, pull request or discussion, read with `gh`, and any other URL is not fetched; a reference that is missing, unreadable or empty is asked about (interactive) or recorded as no independent spec (headless); `review.json` records each reference's source, the tree it was read from and each line's status, and the handover shows them.
23. How a reference's lines count toward "fully verified" (my reading of decisions 20 and 21, made while building slice 2; the user may overrule it): a requirement line is covered when it has a determined status, met, unmet or not applicable; an unmet line needs a blocking finding that cites its id, with a proof. "Not verified", or no entry, is not covered, and a review with an uncovered line is not fully verified. So a review that finds the pull request short of its reference can still post by itself, as a request for changes, but an unmet line never allows an approval. Independence is derived by a script, not claimed by the model: a reference is independent when `reference.json`, written by `requirements.py extract` beside `review.json`, holds at least one requirement line, so a reference with no checkable line (a prose spec) cannot support an auto-approval; and a review whose `intent.sources` names a reference but has no `reference.json` is not eligible. This replaces slice 1's reading of `intent.independent`. A posted review shows each requirement by its number and a short title (the first 60 characters of its text), never the reference's full text or path.
24. An auto-posted review says so (mine, made while building slice 2; the user may overrule it): `review_payload.py`'s footer says "posted by a person who read it first", which is false for a review that posts itself, so `post_reviews.py --auto` replaces that sentence with "posted automatically, because every check ran on both trees and every finding was verified at this head: no person read it first" (or appends it when the body has no footer) and rewrites `payload.json`, so what GitHub receives is what was written down. A review a person posts keeps the old sentence.
25. How decisions 9 and 10 are made safe in `run_checks.py` (mine, made while building slice 4; the user may overrule it): a run where the two trees shared the machine is believed only when it passed, or when the command and the tree settle it (absent, unsupported). A failure or a timeout in it is the check's first run, and the failing side runs again alone as its second, exactly as a flipping check always has: a pass the second time makes the check `flaky` (which never auto-posts), a second failure confirms it, and so a collision between the two runs can never blame the pull request or read as `ok`. (A first version believed the alone run and would have turned a check that really fails once into `ok`: the existing flaky tests caught it. A `removed by the PR` is never rerun, so it is never turned into `flaky`, which would unblock an approval.) The price is that a check which collides with itself (a unit suite on a fixed port) reads `flaky` until it is named `--serial`, so the result says "together, a failure run again alone". A check needing a service runs one tree after the other, by name or command (docker, compose, postgres, psql, mysql, mongo, redis, e2e, playwright, cypress and the like) or by `--serial NAME`; `--sequential` turns the concurrency off. A baseline result is shared only inside a batch, through a folder the batch names (`--share DIR`), by baseline commit, check name, command and shell, and only a pass is shared: a failing baseline is never trusted from another review, so each pull request runs its own and the others do not queue behind it. An install and a producer of files a later check may read (build, compile, generate, prepare, migrate, seed, setup, docker) are never shared, since a skipped one would leave a later check in the baseline tree without its inputs. A shared result older than three hours is not used (`--share-age`). Two reviews that start the same shared check together run it once: the second waits for the first. A shared check is marked "shared" in `checks.json` and the table, and the baseline tree did not run it, which the skill's text must say (slice 6).

## Facts

- Recorded single-pull-request runs cost $2.30 to $2.39 and took 4 to 7 minutes, for a one-line README change (Opus 5.5, Claude Code 2.1.282; `docs/plugin-behavior-tests.md`, ticket 06). A batch of 3 cost $2.72 and took 596 s (ticket 07). Each review starts three reviewers (`code-review`'s two and a risk reviewer, `general-purpose`) and runs every check on both trees; no `model` or effort is given to any subagent.
- `post_reviews.py` is the only poster (`gh api … POST …/reviews`); it takes no yes or event flag and posts what `payload.json` holds, refusing a payload whose commit differs from the review's head and skipping a pull request whose head moved. `review_payload.py` refuses APPROVE for a blocking finding, a check broken or removed by the PR, a merge conflict, a non-approve verdict or the viewer's own pull request, but not for items under `not_verified`; `batch_report.py` reads such an approve as "ready to merge". `gh pr review` and `git push` are in the skill's `disallowed-tools`, and `gh pr edit` too, so no label can be set today.
- A skill's `allowed-tools` grant covers only the turn that invoked it: a post that runs after the turn ended (a batch's fan-out, a typed answer) falls back to the user's own permission settings.
- GitHub: the review API accepts a `commit_id` older than the head and attaches the review to it (it may show as outdated); with "dismiss stale pull request approvals" on, new commits void an approval. A maintainer can push to a user-owned fork's branch only when the author allowed edits (`maintainerCanModify`), and org-owned forks can't be edited that way (third-party reports; GitHub's docs are silent). A `Co-authored-by:` trailer keeps the author's credit.
- This Mac's load average was 46 on 2026-10-01 from `node` processes that are not this session's, so suite timings taken then (100 to 150 s per suite) are inflated; on a quiet machine the full suite took 2 min 15 s for 3.3.1's release, `test_pr_review.py` being about 30 s per Python version.
- How the check runner schedules work (`run_checks.py`, read 2026-10-01): inside one pull request everything is one after the other, base install, head install, base typecheck, head typecheck and so on (:432-433, :210-213); a slot covers a whole `run_checks.py` process, both trees and every check, so with half the cores as slots the rest of a batch's pull requests wait for a lock, polling every second with no timeout and no queue order (:283-309); a check's run times out at 900 s by default, an install included (:379); nothing is shared between the two trees or between pull requests, `node_modules` included, and a result is kept across runs only by pull-request URL, head and baseline (`evidence.py`). A suite needing a database has no service handling in code: services start only after a yes, else the check "could not run" (`checks.md:6`). No two-hour limit is defined anywhere in `plugin/`.
- What `pr-review` reads as intent today (read 2026-10-02): the pull request's body and linked issues, which "are the spec" (`understand-and-review.md:5`), quoted to `code-review`'s Spec axis; the repo's standards, vocabulary and ADRs from the baseline tree (:8); the risk reviewer gets the diff, the checks table and the sensitive files, and no intent; nothing says what to do with no linked issue or spec; `review.json` has no field for what the review was measured against; the request grammar takes no path or notes. The tickets this workflow writes carry `## What to build`, acceptance criteria as checkboxes, "Must not happen" nested items and a "How to verify" line (`to-tickets/SKILL.md:48-63`); `implement` names the ticket in its commit messages (:54), and parallel runs use the branch `<feature>/<NN>-<slug>`; nothing links a pull request to a ticket, and Seams writes no PR description.
- One failure in a full `test_pr_review.py` run on 2026-10-02 while this Mac's load average was 47 to 51 (`node` processes that are not Seams'), output not captured so the test is unknown; it did not recur in four full runs (110 tests, 170 to 225 s each instead of about 30 s on a quiet machine). The wall-clock pacing tests are the suspects: `test_each_minute_stays_under_the_content_budget` failed once before, under the same kind of load.
