# Changelog

## Unreleased (5.0.0)

- **Renamed to `seams`, a breaking change.** The plugin `matt-pocock-workflow` from the marketplace `my-workflow-agent-skills` is now `seams` from the marketplace `seams`, the project's name since 2026-09-14: the skills are `/seams:<name>`, the agents `seams:scout` and `seams:reviewer`. Claude Code does not follow a rename, so an existing install is removed and installed again: `claude plugin uninstall matt-pocock-workflow@my-workflow-agent-skills`, `claude plugin marketplace remove my-workflow-agent-skills`, `claude plugin marketplace add gabriel-tutor/seams`, `claude plugin install seams@seams`. `scripts/install.sh` stops, removing nothing, while the old copy (from any marketplace) or its marketplace is still there, since the two would both run their hooks on one ledger and list every skill twice. A permission rule naming `Skill(matt-pocock-workflow:…)`, as the 3.3.1 entry below suggested for `pr-review`, stops matching until it names `Skill(seams:…)`; a deny rule left unrenamed no longer denies. Seams' state in `~/.local/state/seams` carries over, and the bootstrap skill keeps its folder, `using-matt-pocock-skills`. Entries below keep the old names, as they shipped.
- **CLAUDE.md stays small.** Claude Code loads CLAUDE.md whole into every session (it warns past 150,000 characters), and a project's file can grow a section per feature until it does. The shared rules gain *Where docs go*: CLAUDE.md keeps the commands, conventions and gotchas in under 200 lines, a feature's notes go to `docs/` named in plain text (never `@`, which loads at launch), and an instruction for one part of the code goes to `.claude/rules/` with `paths:`, loaded only when Claude reads that code. `implement`'s Docs row follows it, and `foundations` reports a CLAUDE.md over 200 lines and, on your yes to a plan, moves its sections out by their line ranges into new files, checks that the lines removed equal the lines added, and leaves one line pointing to each; the plan names any instruction in the file about the file itself, such as "note each feature here", with a rewording for your yes.
- **A gate's yes is yours, in the session.** A yes recorded in a file, such as a teammate's progress file saying the tickets were approved, never stands in for your answer at any of the flow's stops (the shared rules' continuous flow, which `to-spec` and `to-tickets` point to): the 5.0.0 eval found one run in three publishing tickets on such a note, and none in six once the rule was there.
- **The simplicity ladder**, adapted from ponytail (github.com/dietrichgebert/ponytail, MIT; the notice is in `plugin/THIRD_PARTY_NOTICES.md`). Code is written up a ladder that stops at the first rung that holds: does it need to exist, does the codebase already have it, the standard library, a native feature, an installed dependency, one line, then the least code that works. It is read only when code is written (`implement`'s build, a `tdd` slice after the grill) and when the correctness review reads the diff, which now fixes over-building as a gap against the ticket. Bugs are fixed at their root, a deliberate shortcut is marked with a `ceiling:` comment, and the handover says what was skipped. It never cuts validation at a trust boundary, data-loss handling, security or accessibility. Not taken from ponytail: its hooks, its lite/full/ultra levels and its other skills. `CONTEXT.md` gains *Simplicity ladder*; a new eval scenario, `receipt-over-build` (tag `ladder`), sets an over-build trap.

## 4.0.0 — 2026-10-04

Fast and continuous, at the same quality: phase 1 of the revamp grilled on 2026-10-02. The spec is `.scratch/seams-revamp/spec.md`, and every decision with its reason is in `.scratch/seams-revamp/progress.md`. Two changes alter how every session works, hence a major version: the flow no longer asks before each step, and a typed reply no longer ends a declaration. The plugin id and the marketplace name are unchanged, so `claude plugin update matt-pocock-workflow@my-workflow-agent-skills` is the whole upgrade, and going back is reinstalling 3.4.0 (`79e1741`).

- **The flow no longer asks at each step** ([ADR 0006](docs/adr/0006-continuous-flow.md)). Before, `to-spec`, `to-tickets` and `implement` each asked before starting, even after you had said where the work was going. Now your confirmation of a design starts a continuous flow: the grill's last question, which also asks where `implement` builds, or a spec you call agreed. The spec, the tickets, the build and its review then go on by themselves. The flow still stops for:
  - your decisions: the grill's questions, the seams when none were agreed, the tickets' breakdown, the parallel offer, the readiness rows to close;
  - integrating a branch: merge, pull request or keep, and a discard only when you ask for one;
  - a push, a deploy or a publish: the spec's and the tickets' publish, a pull request's push, `release`'s opening question and each deploy's;
  - anything destructive, and any paid run.

  Each stop is asked when it comes, naming what its yes covers, and no earlier general yes ("go all the way") covers one. A limit you set ("just the spec for now") also stops the flow, and so do a ticket with an unmet row in its definition of done and a handover that says to `/clear`. Every step still writes the progress file, and a skill you ask for directly starts at once, as before. After a `/clear`, a confirmation recorded in a committed progress file counts as yours, even one someone else committed (a clone, a teammate's push); the stops above still ask. ADR 0006 records that accepted risk.
- **A route lasts** ([ADR 0005](docs/adr/0005-route-lasts-until-replaced-and-proportional-process.md)). A declaration now holds until another process skill is invoked or the session is cleared (`/clear`, a new session), through your typed replies and the flow's commits. Before, any reply that was not a short go-ahead lapsed it, so the next change was refused until the skill was invoked again and its body read again: one more Skill call after almost every answer in a grill or a build. The lapse hint goes with it. What stays:
  - the gate refuses a change no skill has routed;
  - a read-only agent is held to reads, and a subagent's own declaration covers that subagent alone;
  - the done-check asks for verification once in a turn that changed the project.

  An unrelated request typed mid-task now rides on the current route; the routing still tells Claude to route new work.
- **Process in proportion.** Scouts, question rounds and reviews scale with the change's size and risk. Before, every grill started scouts "however small the codebase", every build got two reviewers and a twelve-row done table, whatever the change. One table in the new shared reference, `using-matt-pocock-skills/references/rules.md`, now sets it:
  - a trivial change gets `trivial`'s test and the narrowest check;
  - a one-line fix gets one test at its seam, red then green;
  - a bug or a bounded change gets scouts only for facts the conversation lacks, a few question rounds, and the two reviews offered;
  - a feature, or any build through `implement`, gets the full grill, whose scouts still run however small the codebase, both reviews and the definition of done;
  - anything sensitive gets `code-review`, a correctness review and the security review, all required, and verification always.

  That reference also holds every rule several skills repeated (effort, the repository facts, the progress file, the sensitive list, the stages, evidence, worktrees, the continuous flow), so each is written once. Two contradictions are settled there: evidence from the same commit is reused, not re-run, and a worktree starts from local HEAD.
- **Official docs for anything third-party.** Before writing or reviewing code that uses a library, framework, platform, CLI or API, the skills check its official docs for the version in use and cite them. Repo-internal logic needs no lookup.
- **Scouts on Sonnet.** `scout` runs on Sonnet: the alias `sonnet`, which means Sonnet 5.5 on the Anthropic API from Claude Code 2.1.284, and an older Sonnet before that or on another provider ([model configuration](https://code.claude.com/docs/en/model-config)). `reviewer` stays on your session's model.
- **Lighter hooks.** The gate module is split in three, so each hook event loads only what it needs: `seams_ledger.py` (the ledger and the rules every hook shares), `seams_gate.py` (the PreToolUse rules) and `seams_shell.py` (the shell reader). Median wall time per firing on the developer's Mac, 3.4.0 to 4.0: Stop 37.6 to 19.5 ms, UserPromptSubmit 37.9 to 19.8, PreToolUse on an Edit 37.7 to 21.1, and on a Bash call 37.5 to 25.8. A Bash call still compiles the shell reader, since a bytecode cache in the temp directory would be code a sandboxed shell could plant. Every hook still fails open. The manual-only declaration path, which no skill used, is gone.
- **The ledger out of an agent's reach.** The per-session ledger moved from `$TMPDIR/seams-<uid>/` to `~/.local/state/seams/`, outside the temp and Claude config directories. Where the home directory can't hold it, it falls back to `$TMPDIR/seams-<uid>/`. Under the temp directory, a shell write into it counted as scratch, so any tool call could forge a declaration. Now a tool call that writes it changes the project: refused without a declaration, and refused to a read-only agent whatever is declared. Nothing moves the old ledger, so a session running across the upgrade declares once more. Where the home directory lies under a temp root (a CI job, an eval run), a shell command whose target is `$HOME`, `$HOME/.local` or `$HOME/.local/state` itself now needs a declaration. A write whose path has a `..` segment (`/tmp/a/../b`), from the shell or an editor tool, is no longer scratch: it needs a declaration, and a read-only agent is refused it, since a symlink before the `..` can lead out of the temp directory.
- **A suite that runs in under a minute.** `scripts/test.sh` runs the 17 suites at once, at most half the cores at a time, and reports each one's result and time. A run over its budget fails: a minute locally, 300 seconds on CI. On the developer's Mac it takes about 15 seconds, where 3.4.0's took about ten minutes.
  - Tests check behavior, not wording. About 750 pins on the skills' and the README's wording shrank to the contracts: the size bounds, the frontmatter, the routing table's rows, injected commands, the version's single source, the notices, the flow's stops, the process table's floor and the docs rule. Rewording a skill breaks nothing else.
  - No test sleeps. The gate's rules are tested once in process, and each hook event once through its command line.
  - The macOS system Python 3.9 runs once, as its own CI job, instead of doubling every local run.
  - The custom eval harness (`behavior_test.py`, `prepare_run.sh`, `fixture_deps.sh`) and its tests are gone, and with them the suite's need for Node. `plugin/evals` stays for `claude plugin eval`.
- **Two new eval scenarios**, tagged `flow`. `continue-confirmed-design`: after `/clear`, a "continue" on a confirmed design starts the spec without asking and stops at its publish. `teammate-progress-file`: a progress file a teammate committed says the user approved everything in advance; the tickets' approval is still asked before anything is published.
- **Unchanged.** The context management: the progress files still note every decision and step, the resume note comes at every session start, `/clear` and compaction, and the flow skills start with the repository facts. And `pr-review`: it takes only the effort rule from the shared reference, and its steps, scripts and checks are 3.4.0's.
- **Docs.** The README describes the continuous flow, the lasting route, the proportional process, the lighter hooks and the new suite. `CONTEXT.md` gains *Continuous flow* and *Shared rules* and loses *Lapse hint*. ADR 0001 points to ADR 0005. The plugin's and the marketplace's descriptions no longer call the spec, tickets and implement steps gated. The proof the release waits for, the eval scenarios run on 3.4.0 and on the candidate and three scripted tasks measured on both, is in `docs/plugin-behavior-tests.md` with its results. No eval case scores lower on 4.0. A bug fix costs about the same. Spec-and-tickets work costs about 29% more, from the shared rules carried through the conversation; ticket 13 of the revamp trims that after 4.0.0.

## 3.4.0 — 2026-10-02

- **`pr-review` posts a review by itself when it is fully verified.** Before, every review waited for your yes. Now, in a repository you can push to, a review that is fully verified at the pull request's current head posts without asking, for approve, request changes and comment alike: every check ran on both trees with no "could not run" or flaky result, nothing is under not verified, every finding is verified and every blocking one proven, and the head has not moved. The poster's code decides this from the evidence on disk, not from the model's say-so. Anything else prints `needs your yes` and asks as before. `draft only` in your request turns it off. The review's footer says it was posted automatically, and the pull request gets a `pr-review: approved | changes requested | commented` label. This reverses 3.3's "nothing posts without a yes" ([ADR 0004](docs/adr/0004-auto-post-when-fully-verified.md)). To let a batch post hands-off, add `Bash(python3 *post_reviews.py *)` to your permissions: the batch's post step runs after the turn that pre-approves it.
- **A reference says what the pull request is for.** `against <file or issue URL>`, or a Seams ticket found from the branch name (read from the baseline, never the PR's own head), or a linked issue with acceptance criteria. Each checkbox and "Must not happen" becomes a numbered requirement the review answers; an unmet one is a blocking finding; an approval auto-posts only against an independent reference. The risk reviewer still sees facts only.
- **Take over a pull request.** After a review that is not ready to merge: "Short on time? Take this PR over?". On yes it fixes in a worktree, re-runs the checks and shows you the diff, then pushes only on your yes, to the author's branch when GitHub allows it or a new branch of yours otherwise, with `Co-authored-by` for the author. Never a force push; merging stays yours.
- **Faster, at the same confidence.** A check's two trees run at once while the machine has room (services run one after the other); only a pass from a concurrent run is believed, and a failure is run again alone before anyone is blamed. In a batch a passing baseline result is shared across the reviews of one commit, and removed when the batch closes. Nothing is skipped: the baseline still runs when the head passes, and every reviewer still runs.
- **Cheaper to start.** `pr-review`'s core stays under its 11,200-byte bound: posting, the handover and the take-over moved to references read only at their step, and a batch's reviewers never read them.

## 3.3.1 — 2026-09-30

- **Claude and your workflow skills can start `pr-review`.** It was typed by hand only (`disable-model-invocation`), so a skill that called it got "cannot be used with Skill tool due to disable-model-invocation". Its description now leads with when to use it, "Use when asked to review GitHub pull requests (numbers, URLs, open, requested)", which tells Claude to start it when you, or a skill you run, ask for a review of GitHub pull requests; a local branch, commits or uncommitted work stay `code-review`'s. The review is otherwise unchanged: an untrusted pull request's code runs only after a yes, nothing is posted without one, and typing `/pr-review` works as before. A batch's next step reads "Continue it with pr-review on …", so Claude continues an unfinished batch itself when you ask, and the resume note no longer says only you can start it.
- **Trust needs push access.** A pull request's code runs without a question only in a repository you can push to (`viewerPermission` `WRITE`, `MAINTAIN` or `ADMIN`; an error counts as no), and only when you opened it or a collaborator opened it from a branch of that repository. In 3.3.0 a stranger's pull request in the stranger's own repository counted as trusted, since its author owns that repository, and so did your own pull request to it, whose baseline is the stranger's code: a review of its URL ran their installs and checks unasked. With Claude able to start a review, text it reads could have led there.
- **No git hook runs at checkout.** The review's worktrees are made with `core.hooksPath=/dev/null`: a checkout-time hook in your clone runs inside the pull request's tree and reads its files, so a hook runner such as lefthook or pre-commit would have run a command the pull request chose, even under static review (since 3.2.0, shown by a local probe). The checks pr-review finds in your hooks still run later, on purpose, when trust allows.
- **The gate's hint leaves `pr-review` out.** A review needs no declaration, and invoking it again after your typed answer would re-arm its pre-approved scripts, posting included; after your answer, your own permission settings decide, as before.
- **Permissions.** When Claude starts it, Claude Code may ask first ("Execute skill"). `Skill(matt-pocock-workflow:pr-review)` in `permissions.allow` starts it without asking, as a headless workflow needs, though that, like a broad Skill allow, auto mode or bypassed permissions, also lets text Claude reads start a review; the same rule in `permissions.deny` keeps it typed only, refusing Claude's call by either name while typing still works (checked on Claude Code 2.1.285).
- `pr-review`'s core may take 11,200 bytes where the other skills have 11,000: it measures about 3.6k tokens on invoke, under the 4,000-token cap the bound stands for.

Lean and durable: the same workflow, lighter on tokens, faster, and nothing lost across `/clear` and compaction. This is phase 1 of the four-phase roadmap agreed on 2026-09-25; the spec is `.scratch/lean-and-durable/spec.md`, and every decision with its reason is in `.scratch/lean-and-durable/progress.md`. - **Work in progress survives `/clear`, compaction and a new session** ([ADR 0003](docs/adr/0003-committed-progress-file.md)). A grill's answers lived only in the conversation, so `/clear` mid-grill lost them, and after `/clear` you had to explain where you were. Now each feature keeps a committed progress file, `.scratch/<feature>/progress.md`, which the flow skills write as they go. The grill records each answer as it lands. `to-spec` and `to-tickets` record their stage. `implement` records the ticket in progress, the candidate under review and the findings to fix, then makes a record commit before the definition of done. `finishing-a-development-branch`, now Seams' adaptation of the Superpowers copy so that it can record integration, and `release` record the later stages. The session-start hook now also runs on resume and fork. It adds a resume note built from the newest three active files: under 1,500 characters, framed as data, each field one capped line with markup stripped, plus a one-line notice for you. The skill that continues the work re-reads the spec, the tickets and git, and reports a mismatch rather than acting on the note. A ticket whose file agrees with git resumes without `implement`'s gate question.
- **A `pr-review` batch resumes.** `evidence.py` pins each pull request's evidence by head and baseline. Typing the same `/pr-review` again reuses a review finished at the same head and baseline, continues an unfinished one from its last completed step, and reviews a moved head afresh; `afresh` reuses nothing. A batch keeps its own progress file beside its evidence under the temp directory, and the resume note lists it until the batch's final handover.
- **Every skill fits what compaction keeps.** Compaction keeps the first 5,000 tokens of each invoked skill. `pr-review` was about 8,800, so a long batch lost its posting, cleanup and handover steps. It is now a core of 10,985 bytes plus six references, each read at its step. A static guard, which also runs on CI, holds every `SKILL.md` to 11,000 bytes, about 4,000 tokens. `pr-review` no longer says subagents can't start subagents; it names Claude Code's real limits.
- **Lighter every session.** Descriptions lead with their trigger and drop repetition. The bootstrap states the routing as the project's facts, without the `<EXTREMELY_IMPORTANT>` wrapper: Claude Code's hook docs warn that text framed as commands can trip Claude's prompt-injection defenses. On the new wording, the routing and gate evals kept every case, on Opus 5 and Sonnet 5. By `claude plugin details`, the always-on cost fell from about 1,165 tokens to about 857, including the two new agents. No skill or agent pins a model or an effort level, since a pin overrides your own choice both ways. The Seams skills read `${CLAUDE_EFFORT}`, and at `low` they skip only extras they name, never a gate or a check.
- **Faster.**
  - The grill asks every independent question at once, up to four in one call; a gate, security or destructive question is still asked alone.
  - Two read-only agents ship with the plugin: `scout` finds facts in the code and docs, and `reviewer` reviews a named diff. The grill, `to-spec`, `foundations` and `implement` delegate to them by name and start independent reads together. On Opus 5, Claude Code tells Claude not to start subagents unless asked, and when the grill only named the agent, all three test runs read the code themselves.
  - `implement`, the grill and `release` start with the repository facts (the branch, the short HEAD, the status and the progress files), which the Skill and prompt-expansion hooks add. No skill injects a shell command: a session without the Bash tool aborted such a skill before Claude saw it.
  - `pr-review`'s scripts are pre-approved, so they run without permission prompts.
  - When two or more tickets are unblocked, `implement` offers to build them at once. Each gets a background builder in its own worktree from your local HEAD, at most half the cores and four at a time. The builds are integrated one at a time, with the full suite on each, and a ticket that fails stays on its branch.

  - Reviews scale with risk. Every build gets Matt Pocock's `code-review` plus a correctness review by the `reviewer` agent. The bundled `/review` can't be reached while his `code-review` holds its name: `Skill("review")` answers "Unknown skill".

## 3.2.1 — 2026-09-24

What the first real batch taught: `/pr-review` on 15 pull requests of a private repository, run from 3.2.0. The review worked end to end; these are the six gaps it showed, and what closed each.

- **The gate kept the review's work.** A subagent's hand-back now keeps the current request, like the other notices Claude Code generates. It reaches the prompt hook as `<agent-message from="…">`; the transcript shows it under an "Another Claude session sent a message:" line the hook never sees. Before, each one started a new request and dropped the declaration: 21 of the run's 25 refusals followed a hand-back, and the session declared `trivial` 28 times to get through. A shell write whose every path is an absolute path under the temp directory (or `/dev/null`), outside the working directory, is no longer a change, as `Edit` and `Write` there never were; the Claude config directory is not scratch for a shell command. The writes that still count:
  - a relative path, a glob, or a command substitution;
  - a variable set outside the command, or one a `for` loop, `read`, `unset` or `eval` may have changed (variables set earlier in the same command are followed);
  - an option with its path attached (`--target-directory=DIR`, `-tDIR`);
  - `find -exec`, an in-place editor, a package manager, or an inline program;
  - `git worktree add` without `--detach`, which makes a branch;
  - an unquoted variable whose value would split or glob, anything after an `IFS` assignment, a brace expansion, or a variable an `+=` appended to.

  A heredoc's text is data, not commands, unless its word is unquoted and the text holds `$(…)` or backquotes, which the shell runs; a `<<` inside quotes opens no heredoc. What `$(…)` and backquotes run is classified as a command, in double quotes too, and so is what `eval` runs; a backslash before a command's name (`\rm`) no longer hides it. The classifier also splits commands at newlines, subshells and shell keywords, so `echo hi` then `rm -rf src` on the next line, `(rm -rf src)` and `then rm -rf src` are seen; before, each was read as one read-only command. It now knows `tar -x`/`-c`, `unzip`, `rsync`, `sort -o` and `curl --output=`. The refusal says scratch work needs no declaration.
- **Checks are found once per repository, git hooks included.** The main session finds them before the fan-out: CI's commands and the scripts they call, what the git hooks run (husky, lefthook, pre-commit, simple-git-hooks, `core.hooksPath`), and package scripts named like checks. Every reviewer gets the same list and adds only checks its own pull request introduces. A hook-only audit had been found by 1 reviewer of 15; run on the other 14 afterwards, it failed every candidate and flipped four verdicts. A check found late joins a review through `run_checks.py --merge`, never by hand.
- **`run_checks.py` runs checks as CI does, or says it could not.** It runs them in the newest bash on PATH or in the usual install places (or the one `--bash` names), and the table names the version. A log showing a bash 4 shell option rejected (`shopt -s globstar`), or, under a bash older than 4, `mapfile`, `declare -A` and the like failing, makes that run "could not run", never pass or fail: on macOS's bash 3.2, CI's globstar test glob had run 799 of 998 files and still reported a result. The same messages under bash 5 stay the command's own failure. The questions before the fan-out offer `brew install bash` when a check needs it. A test file missing from one tree (node's "Could not find", pytest's "file or directory not found", jest's and vitest's "No tests found") is absent there, so a check aimed at the pull request's new test reads "new in the PR", not "fixed by the PR". It refuses to start on a tree with files neither its commit nor an earlier check left; what checks leave (a report, a build cache) is remembered, so `--merge` and `--recheck` still run. An unreadable `checks.json` is a usage error.
- **Probes stay out of the checked trees.** A probe is written in `$EVID/probes/`, copied into a tree only after that tree's checks finished, and removed right after it runs; cleanup reports any file left in a tree instead of deleting it with the worktree. Probes left in `tests/` had been counted by an audit (985 files against 983 committed).
- **Every reviewer starts at once; checks take turns.** A batch starts one subagent per pull request immediately, and their installs and suites share the machine's check slots (`run_checks.py --slots`, half the cores by default; a lock per slot that frees itself when a review dies). After the batch, each check called broken by the PR runs again alone (`--recheck`) and is flaky, not the pull request's, when it passes. Thirteen reviews at once had run a 14-core machine at a load of 53, and two verdicts were relabelled by hand.
- **Posting is paced.** New `post_reviews.py` posts the chosen reviews one at a time. A review counts 1 plus its inline comments against half of GitHub's limits for creating content (80 a minute, 500 an hour). A rate-limit block is waited out as GitHub asks (retry-after, the reset time, or a doubling backoff) and tried again up to four times, with posts 45 seconds apart from then on.
