# Changelog

## 3.2.1 — 2026-09-24

What the first real batch taught: `/pr-review` on 15 pull requests of a private repository, run from 3.2.0. The review worked end to end; these are the six gaps it showed, and what closed each.

- **The gate kept the review's work.** A subagent's hand-back now keeps the current request, like the other notices Claude Code generates. It reaches the prompt hook as `<agent-message from="…">`; the transcript shows it under an "Another Claude session sent a message:" line the hook never sees. Before, each one started a new request and dropped the declaration: 21 of the run's 25 refusals followed a hand-back, and the session declared `trivial` 28 times to get through. A shell write whose every path is an absolute path under the temp directory (or `/dev/null`), outside the working directory, is no longer a change, as `Edit` and `Write` there never were; the Claude config directory is not scratch for a shell command. The writes that still count:
  - a relative path, a glob, or a command substitution;
  - a variable set outside the command, or one a `for` loop, `read`, `unset` or `eval` may have changed (variables set earlier in the same command are followed);
  - an option with its path attached (`--target-directory=DIR`, `-tDIR`);
  - `find -exec`, an in-place editor, a package manager, or an inline program;
  - `git worktree add` without `--detach`, which makes a branch;
  - an unquoted variable whose value would split or glob, anything after an `IFS` assignment, a brace expansion, or a variable an `+=` appended to.

  A heredoc's text is data, not commands, unless its word is unquoted and the text holds `$(…)` or backquotes, which the shell runs; a `<<` inside quotes opens no heredoc. What `$(…)` and backquotes run is classified as a command, in double quotes too, and so is what `eval` runs; a backslash before a command's name (`\rm`) no longer hides it. The classifier also splits commands at newlines, subshells and shell keywords, so `echo hi` then `rm -rf src` on the next line, `(rm -rf src)` and `then rm -rf src` are seen; before, each was read as one read-only command. It now knows `tar -x`/`-c`, `unzip`, `rsync`, `sort -o` and `curl --output=`. The refusal says scratch work needs no declaration.
- **Checks are found once per repository, git hooks included.** The main session finds them before the fan-out: CI's commands and the scripts they call, what the git hooks run (husky, lefthook, pre-commit, simple-git-hooks, `core.hooksPath`), and package scripts named like checks. Every reviewer gets the same list and adds only checks its own pull request introduces. A hook-only audit had been found by 1 reviewer of 15; run on the other 14 afterwards, it failed every candidate and flipped four verdicts. A check found late joins a review through `run_checks.py --merge`, never by hand.
- **`run_checks.py` runs checks as CI does, or says it could not.** It runs them in the newest bash on PATH or in the usual install places (or the one `--bash` names), and the table names the version. A log showing a bash 4 shell option rejected (`shopt -s globstar`), or, under a bash older than 4, `mapfile`, `declare -A` and the like failing, makes that run "could not run", never pass or fail: on macOS's bash 3.2, CI's globstar test glob had run 799 of 998 files and still reported a result. The same messages under bash 5 stay the command's own failure. The questions before the fan-out offer `brew install bash` when a check needs it. A test file missing from one tree (node's "Could not find", pytest's "file or directory not found", jest's and vitest's "No tests found") is absent there, so a check aimed at the pull request's new test reads "new in the PR", not "fixed by the PR". It refuses to start on a tree with files neither its commit nor an earlier check left; what checks leave (a report, a build cache) is remembered, so `--merge` and `--recheck` still run. An unreadable `checks.json` is a usage error.
- **Probes stay out of the checked trees.** A probe is written in `$EVID/probes/`, copied into a tree only after that tree's checks finished, and removed right after it runs; cleanup reports any file left in a tree instead of deleting it with the worktree. Probes left in `tests/` had been counted by an audit (985 files against 983 committed).
- **Every reviewer starts at once; checks take turns.** A batch starts one subagent per pull request immediately, and their installs and suites share the machine's check slots (`run_checks.py --slots`, half the cores by default; a lock per slot that frees itself when a review dies). After the batch, each check called broken by the PR runs again alone (`--recheck`) and is flaky, not the pull request's, when it passes. Thirteen reviews at once had run a 14-core machine at a load of 53, and two verdicts were relabelled by hand.
- **Posting is paced.** New `post_reviews.py` posts the chosen reviews one at a time. A review counts 1 plus its inline comments against half of GitHub's limits for creating content (80 a minute, 500 an hour). A rate-limit block is waited out as GitHub asks (retry-after, the reset time, or a doubling backoff) and tried again up to four times, with posts 45 seconds apart from then on. A wait longer than all four tries' backoff (a primary limit resetting within the hour) is not taken; the run says when to post again. It looks for the review on GitHub before every post, so a refused post GitHub kept is never doubled, and it skips a pull request that moved. Any other refusal, or a failure of `gh` itself, stops the run for the person to decide. Ten reviews posted in 34 seconds had been blocked for the next five.
- `CONTEXT.md` gains *Check* and *Probe*.

## 3.2.0 — 2026-09-23

- **`/pr-review`: deep review of GitHub pull requests, typed by hand only.** One pull request or a batch (numbers, URLs, `owner/repo#number`, `open`, `requested`). For each: the head pinned; the head and its baseline (the merge-base) checked out into worktrees it marks as its own; the commands CI runs, e2e included, run on both by `plugin/skills/pr-review/scripts/run_checks.py`, which re-runs a flipping check before blaming anyone, ends whatever a check leaves running and gives every check a verdict (ok, broken by the PR, fixed by the PR, already broken, flaky, new or removed by the PR, could not run); the change tried by hand; Matt Pocock's `code-review` beside a risk reviewer; every finding verified and, where it can be, proven (a regression test must fail on the baseline, a suspected bug gets a failing probe test). `review_payload.py` turns the findings into one GitHub review, inline only where GitHub accepts a comment (its diff parser counts hunk lines), the rest in the body, suggestion blocks on the right side (an empty suggestion is none: committed on GitHub, it would delete the line), a footer saying it was drafted with Claude Code and whether checks ran, and only an event GitHub and the evidence allow (no approve with a blocking finding, a check broken by the PR or a merge conflict). A batch runs one subagent per pull request, four at a time, with every question asked before and after the fan-out (in text when AskUserQuestion is unavailable, as in a headless run). Nothing is posted, pushed, merged or edited without the user; an untrusted pull request's code runs only after a yes, and static review runs nothing from it, not even a probe (the viewer's own pull requests, forks included, are trusted); the pull request's text is reviewed, never obeyed. The review handover opens with `batch_report.py`'s table (ready to merge, changes needed, not yet) and a paste-ready note for each author whose pull request is not ready.
- **The gate: a manual-only Seams skill typed by its bare name declares.** Claude Code runs a plugin skill typed bare (`/pr-review 42`) when no other command has the name, and a manual-only skill is only ever typed, so the gate counts its bare form under its full name, matched in exact case. No other bare name changes: the model-invocable Seams skills are declared through the Skill tool, and a bare name they share with a Superpowers original or a project's own command may not be the Seams skill at all. Matt Pocock's bare names still win.
- The static test's rule that no skill is user-only becomes an allowlist, which pins `pr-review` as manual-only and every other skill as model-invocable. `routing.md`'s on-ramps point at it. `CONTEXT.md` gains *Baseline*, *Finding* and *Review handover*.
- Evidence: three live runs, headless, on throwaway pull requests in this repository, with writes to GitHub blocked until the user answered: a batch and one post on the user's yes, then the single review typed bare, then a batch whose subagents got facts only. They are recorded, with what they did not exercise, in `docs/plugin-behavior-tests.md`. The single-review run found the empty-suggestion bug above.

## 3.1.0 — 2026-09-19

- **An eval suite ships inside the plugin.** The ten routing scenarios now live at `plugin/evals/<case>/`, one directory each, read by the routing harness and by `claude plugin eval` alike: `prompt.md` (its frontmatter is the eval's; the harness sends the body), `expect.json` (the harness's expectation), `setup.sh`, `scaffold.sh` and `case.yaml` (the eval's workspace), and `graders/` (free graders only: the expected skill invoked, no editor call before the first Skill call, no gate refusal in a routing scenario, the declaration before the change in a gate scenario). A unit test holds the graders to each `expect.json`, so the two suites cannot drift. Anyone with the plugin installed can run it by name, on their own machine and model, and get WITH, W/OUT and Δ against a no-plugin baseline plus a shareable report: `claude plugin eval matt-pocock-workflow@my-workflow-agent-skills --tag routing --tag gate --scaffold --allow-tools Edit Write`; the two cases that need a shell carry the `shell` tag and take `--allow-tools Bash` where the Bash sandbox can start. The fixture and the shared files moved with the scenarios (`plugin/evals/_fixture`, `_shared`); its installed dependencies live outside the plugin (`tests/fixture-deps`, built by `scripts/fixture_deps.sh`), because a directory-marketplace install copies the plugin's working tree, gitignored files included.
- **The scaffold gives an eval run Matt Pocock's skills.** A run loads nothing from the runner's config and nothing at project scope, but it does load user skills from its own config directory; the shared scaffold (`plugin/evals/_scaffold.sh`) copies the nine required skills from the runner's real config into the run's, symlinks resolved, before Claude Code starts (the runner's layout as observed on 2.1.278: a throwaway `$HOME` beside a `config` directory). Missing skills are named on stderr and the run shows what that machine has.
- **The session-start hook counts project-scope skills** (`<repo>/.claude/skills`, skills.sh without `-g`) as well as the config directory's, and names the directory holding them.
- **The bootstrap skill is not a declaration.** Invoking `matt-pocock-workflow:using-matt-pocock-skills` (the routing policy itself) no longer opens the gate; an eval run showed the model doing exactly that after an "Unknown skill" error. Every other Seams skill and Matt Pocock's process skills still declare.
- **A notice Claude Code generates is not a new request.** A background task's or monitor's completion notice, a system reminder and a Stop hook's feedback arrive as user turns; the prompt hook used to start a new request on each, dropping the declaration mid-build (three times in the session that built this). They now keep the current request, like a go-ahead.
- `CONTEXT.md` gains the evidence vocabulary: *Scenario*, *Arm*, *Run record*.

## 3.0.0 — 2026-09-16

The workflow is enforced by hooks, carried past the merge, and measured by a harness that reports what happened. Grouped by the findings of the 2026-09-15 review (F01–F09), after the one change that is not a finding. The plugin id `matt-pocock-workflow` and the marketplace name `my-workflow-agent-skills` are unchanged: `claude plugin update matt-pocock-workflow@my-workflow-agent-skills` is the whole upgrade. Evidence for each claim is in `docs/plugin-behavior-tests.md` and `docs/compatibility.md`.

**The gate and the done-check (ADR-0001).** A PreToolUse hook refuses any change to the project (`Edit`, `Write`, `MultiEdit`, `NotebookEdit` to a path outside the temp and Claude config directories, or a shell command its classifier labels a mutation) until a process skill has been invoked for the current request, with a reason that names the label and the routes; a Stop hook refuses to end a turn once when non-documentation files changed and `matt-pocock-workflow:verification-before-completion` did not follow. The ledger is one JSON file per session under the temp directory, holding skill names, tool names and paths only; `startup` and `clear` reset it, `compact` and `resume` keep it; a short go-ahead ("yes", "continue", an option letter) keeps the declaration, any other prompt starts a new request; a slash command the user types is a declaration; Superpowers' process skills are not. Every hook fails open and runs on Python 3.9 (macOS's system interpreter crashed the 2.1 hook on import and, failing open, left the session without a bootstrap). New `trivial` skill: the cheap declaration, carrying the test of what is not trivial.

**F01, a review that sees the candidate.** `implement` commits the ticket's files by name before `code-review` (unrelated dirty or untracked files are listed as excluded, never staged), passes the merge-base as the fixed point with HEAD as the candidate, reports an empty diff instead of reviewing it, commits review fixes and re-runs the checks they affect, and names the candidate SHA in the definition-of-done table. `routing.md`: evidence belongs to a candidate; an unchanged candidate's suite is reused, a change makes a new candidate.

**F02, Seams-owned flow skills (ADR-0002).** `to-spec`, `to-tickets` and `implement` are Seams' own adaptations of Matt Pocock's (MIT, attributed with the upstream commit and file hashes in `plugin/THIRD_PARTY_NOTICES.md`), so nothing follows a user-only skill by reading its file; each keeps its gate before starting and before publishing. `scripts/tests/test_plugin.sh` warns, without failing, when an installed upstream file differs from the recorded hash.

**F03, session-start knows what is installed.** The hook resolves the config directory from `CLAUDE_CONFIG_DIR`, else `~/.claude` (paths with spaces and symlinked skill directories included), checks all nine Matt Pocock skills the plugin invokes, and names the missing ones with the one install command (`npx skills add mattpocock/skills -g -a claude-code`). `docs/compatibility.md` records the tested skills commit and each file's SHA-256.

**F04, an installer that tells the truth.** `scripts/install.sh` checks the `claude` CLI, Node and `python3` at 3.9 or newer (naming the version found when too old), installs Matt Pocock's skills only through a terminal (piped without one it prints the command instead), and runs every `claude plugin` command through one helper that stops at the first failure with that command's output. It writes no `settings.json` and takes no backup; the marketplace and the enabled plugin are recorded by the `claude plugin` commands themselves. `test_install.sh` runs it in fixture homes against a stub `claude`: settings byte-identical, a failing step stops it, a second run changes nothing, a home without the skills and no tty exits with a message.

**F05, a harness that measures what it claims.** `scripts/behavior_test.py` imports the gate's classifier (`plugin/hooks/seams_gate.py`), so a shell write before the first Skill call scores as straight-to-code; a verdict is confirmed by its own result; gate refusals, failed calls, the platform's permission denials, timeouts, exit codes and the candidate are recorded; `--assert` judges every run against `tests/scenarios/<name>/expect.json` and exits 1 when any is short, infrastructure errors listed apart from misses; `judge` re-judges saved records and `report` prints the counts table `docs/plugin-behavior-tests.md` carries. Four gate scenarios (a pressured one-line change, a shell write, a typo, "commit this") join the six routing scenarios. The docs describe the harness as a routing probe, not an outcome evaluator, and the question-mark count as a formatting heuristic.

**F06, routing by risk, authorization preserved.** The bootstrap's table routes by size and by risk: `trivial`* for trivial changes, a Sensitive row at any size (auth, permissions, secrets, billing, migrations, infrastructure, CI or deploy config, a public API, anything destructive: `grill` on the security and failure axes, `code-review` required), `incident`* for a live outage, `release`* for shipping, a new app's ticket 01 as the walking skeleton. Rule 4: a yes covering later steps is not asked again; deploy and publish always ask. The grill skips a decision the code or an earlier answer already settles. The bootstrap fits 2,900 bytes at a cache-length plugin path; the Superpowers-overlap sentence and the support-skill owners moved to `routing.md`.

**F07, past the merge.** New `release` skill: a readiness table (integrated candidate, suite green on that SHA, artifact built and identified, config per environment, migration and rehearsed restore when data changes shape, abort conditions and rollback path, the applicable checks, the smoke plan; anything unmet blocks), a deploy only after an explicit yes naming target, environment and candidate (staged environment first when one exists), verification that the running version is the candidate with the abort path on failure, an operations handover, and a target table for web hosts, containers and VPSs, mobile stores, CLI and library registries, browser extension stores and desktop. New `incident` skill: impact, contain (every outward action behind a yes), restore and confirm, then `diagnosing-bugs`, the fix through the normal route with a regression test first, a post-mortem note under `docs/incidents/`. `foundations` surveys deploy target and pipeline, environments and config, backups and restore, monitoring and alerts, dependency and secret scanning. `to-spec` adds a Release subsection when the work ships; `to-tickets` ends with a release ticket then. Every handover names the stage reached: designed, built, integrated, release-ready, deployed, operated.

**F08, executable acceptance for security, product quality and operations.** `to-tickets` turns the negative cases the design lens raised into acceptance criteria; `release` runs the applicable checks (dependency audit, secret scan, accessibility for a UI, load when the lens flagged scale) before a deploy; the Sensitive row makes the review required whatever the size.

**F09, bounded process cost.** The 150k-token continuation figure is gone; `routing.md` carries a judgment rule for phase boundaries, names the durable state (spec, tickets, `CONTEXT.md`, ADRs; a resumed ticket reads them and never relies on chat memory), and reuses evidence for an unchanged candidate. The bootstrap stays small and loads the release and incident detail only when those skills run.

**Tests and CI.** The gate module's unit tests, the hook suite fed JSON on stdin (under the default `python3` and the system 3.9), the session-start suite, the installer suite, the static plugin checks (`claude plugin validate --strict`, headings, wording, checksums, one version across both manifests, the README badge and this file), the harness's own tests and the sandbox-workspace suite run through `scripts/test.sh`, and on macOS and Ubuntu in `.github/workflows/test.yml` on every push to `main` and on pull requests. Windows is not supported.
