# Reference

What a pull request is meant to do, from a source its author did not write. The main session finds it, after each checkout and before any reviewer starts (a batch: in the question round, so a subagent receives `reference.json` and never asks).

1. **Sources.** In this order, all that exist: what the request names (`against <path | URL>`: a file, or a GitHub issue, pull request or discussion URL, read with `gh issue view`, `gh pr view` or `gh api`; any other URL is never fetched, ask for its text); a Seams ticket or spec under `.scratch/` that the pull request's branch (`<feature>/<NN>-<slug>`: `.scratch/<feature>/issues/NN-<slug>.md`) or its commit messages name; a linked issue (`closingIssuesReferences`) that has acceptance criteria. Read a file from the baseline tree (`$EVID/base`), never the head: a pull request cannot edit its own acceptance, and a spec that exists only in the head is the author's own words, not a reference. Precedence: the reference, then a linked issue, then the pull request's body. A disagreement between them is a finding, and so is a body that claims more or less than the reference.
2. **Lines.** Write each source's text with the Write tool under `$EVID/reference/`, then `python3 <skill-dir>/scripts/requirements.py extract --out "$EVID/reference.json" --source "<label>" "<file>" ...` (a label says what it is: "ticket 07 at the baseline", "issue #13"). A script numbers the lines `R1`, `R2`, ... from the checkbox criteria and the "Must not happen" items, keeps its how to verify items apart, and records each source by its label and hash, never its path. A reference with no checkbox (prose) has no lines: it cannot support an approval.
3. **No reference** beyond the pull request's own description: a single review asks once, with AskUserQuestion, for a ticket, a path, or "go ahead" (the description is the intent). A batch or a headless run goes ahead and records the note in `review.json`'s `intent` and in the summary, not under not verified.
4. **Use.** The Spec axis of `code-review` is given the reference (the lines and what each source is), and the risk reviewer gets facts only: it never sees it. The main session answers each line in `review.json`'s `requirements` (`met` with evidence, `unmet` with a blocking finding whose `requirement` is the id, `not applicable` with why, `not verified` only when it could not be settled) and runs those how to verify items as checks when trust allows (`run_checks.py --merge --check`). The posted review names a line by its number and short title and never pastes its text.
