# Batch

With several pull requests, Understand, Checks, Review and Draft run in parallel, one subagent per PR. Claude Code's limits set the shape:

- A subagent can't ask the user anything: AskUserQuestion is not among its tools.
- A subagent can start subagents of its own, up to three levels below the main conversation by default (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`).
- At most 20 subagents run at once in a session by default (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` changes it). Past that, the Agent tool fails with `Concurrent subagent limit reached`, and another starts only when one finishes.
- A wide fan-out can hit the API's rate limits. Claude Code retries a throttled request; a background subagent that still ends on one is marked failed, with its last output.

So each pull request gets one subagent, which walks every review axis itself instead of starting reviewers of its own: a batch of fifteen runs fifteen subagents, not forty-five. The fan-out ends this turn: what the main session runs after a reviewer's notification wakes it (the rechecks, a rebuilt payload, the handover's table, a post) is outside the skill's pre-approval, and the user's own permission settings decide.

**The batch's progress file.** With more than one pull request, `evidence.py pin` writes it at the evidence root, in the progress-file shape: the session's repository, each pull request with its step (pinned, checked, reviewed, drafted, posted), and the command that continues the batch. Each step is read from the evidence itself. Each of `run_checks.py`, `review_payload.py` and `post_reviews.py` brings it up to date as its step ends, with no call of its own, and `batch_report.py --close` closes it at the final handover, once every review in it is drafted or posted. While it is open, each new session in this repository lists it in the resume note, so a `/clear` or a compaction loses nothing: typed again, the same command continues the batch, and `evidence.py` says where each review starts.

1. **Find the checks once per repository,** as `checks.md` says, from the base branch, and show the list: the same checks run on every pull request of that repository.
2. **Every question first,** in one round in this session after every checkout (four per call), for the pull requests that still run something (a reused one, or one that continues at Draft, asks nothing): the trust questions from the Gate; for each pull request whose head worktree defines services (a compose file) that its end-to-end suite needs, whether to start them; and, when a check needs bash 4 or newer (`shopt -s globstar`, `mapfile`, associative arrays) while the newest bash here is older (macOS ships 3.2), whether to `brew install bash` first (recommended: without it those checks read could not run).
3. **Start every reviewer, all at once:** one subagent per PR that is new, afresh or continues with its checks, each with the Agent tool (general-purpose, in the background); when Claude Code refuses another (`Concurrent subagent limit reached`), start it as one finishes. Reading and reviewing run in parallel; installs and suites take turns through the machine's check slots (`run_checks.py --slots <n>`: half the cores unless the request says otherwise, "4 slots"), and each suite's own parallelism drops to the cores divided by the slots, only through a flag its runner surely accepts (`node --test --test-concurrency`, jest's or vitest's `--maxWorkers`, `make -j`, pytest's `-n` only with pytest-xdist installed); otherwise CI's command runs as it is. A pull request that continues at Draft gets its payload built here (`draft-and-post.md`), and a reused one goes straight to Post.
4. **Give each one facts only:** the pull request's facts from the Gate, its trust and services answers, `$EVID` and its two worktrees, the repository's path, the viewer's login, the checks list for its repository, the slot count and the test workers, a free port of its own for anything it serves, this skill's directory, and where its review starts, as `evidence.py` said. No review hints: do not summarize the diff for it or suggest what to look for; its review is its own.
5. **Its instruction:** read `<skill-dir>/SKILL.md`, then `references/understand-and-review.md`, `references/checks.md` and the Draft part of `references/draft-and-post.md` beside it (in all four, `${CLAUDE_SKILL_DIR}` and `<skill-dir>` stand for this skill's directory), and carry out Understand, Checks, Review and Draft for this one pull request, from where its review starts, with three differences. It never asks the user anything: a decision it cannot make becomes a question in the review, or a line under not verified. It never posts, and never pushes, merges or edits anything on GitHub. It walks every review axis itself, one after another: Standards and Spec as Matt Pocock's `code-review` describes them (its SKILL.md is in the user's Claude config directory, under `skills/code-review/`), then the risk axes. It runs the checks list as given, adding only checks its own pull request introduces (a new CI step, hook or script), and says which. It ends by writing `$EVID/review.json` and replying with the verdict in one line.
6. **A subagent that fails or times out,** a rate limit included: write the reason to `$EVID/error.txt`. That pull request reads "not yet: could not review" and the rest go on.
7. **After the last one finishes,** with nothing else running: every check a reviewer called broken by the PR, in this run or in a reused review whose `checks.json` has no run of it alone, runs again alone, one pull request at a time (a reused review whose trees are gone gets them back first, and its install check runs again, with `--merge`): `python3 <skill-dir>/scripts/run_checks.py --base "$EVID/base" --head "$EVID/head" --out "$EVID/checks" --recheck <name>`. A check that passes alone is flaky, not the pull request's: work that review's verdict out again by the Review rules, drop a finding that rested only on the check, and rebuild its payload with `review_payload.py`. A check found after the reviews finished runs on each pull request's trees with `run_checks.py ... --merge --check "<name>=<command>"`, and each payload is rebuilt the same way: a review's evidence changes through the scripts, never by hand.
