# Draft and post

## Draft

1. **review.json.** Write `$EVID/review.json`: `{"pr": {"repo", "number", "url", "title", "author", "head", "mergeable"}, "verdict", "summary", "findings": [{"severity", "title", "body", "path", "line", "end_line", "side", "suggestion", "evidence"}], "not_verified": [...]}`. Paths are relative to the repository root; lines are the candidate's (side RIGHT), or the baseline's for a removed line (side LEFT). The summary is three sentences at most: what the pull request does, whether it does it, and the one thing to fix first. A finding with nothing to suggest leaves `suggestion` out; a deletion is proposed in words (an empty suggestion block deletes lines on GitHub). No local paths, machine names or secrets anywhere in it.
2. **The review GitHub receives.** `python3 <skill-dir>/scripts/review_payload.py --diff "$EVID/pr.diff" --review "$EVID/review.json" --checks "$EVID/checks/checks.md" --event <the verdict's event> --viewer <login> --out "$EVID/payload.json" --preview "$EVID/review.md"` (without `--checks` under static review). It anchors each finding inside the diff (GitHub rejects the whole review when one comment misses) and moves the rest to the body under outside the diff, turns suggestions into suggestion blocks, ends the body with a one-line footer saying the review was drafted with Claude Code and whether checks ran, and refuses an event GitHub or the evidence does not allow (the author of a pull request can only comment on it; approve is refused with a blocking finding, a check broken by the PR or a merge conflict). The verdict's event is `REQUEST_CHANGES`, `APPROVE` or `COMMENT`; on the viewer's own pull request it is `COMMENT`.

## Post

1. **Show the draft.** Every pull request's `review.md` in full: the body and each inline comment with its place.
2. **Re-check the candidate** just before asking: `gh pr view <n> --repo <owner/repo> --json headRefOid`. A pull request that moved since the review is stale: say so, offer to review the new head, and do not post it.
3. **Ask, every time.** With AskUserQuestion, naming the pull request, the candidate and the event. A single review: "Post this review to owner/repo#n at <sha7> as <event>?", options: the verdict's event (recommended), `COMMENT`, `REQUEST_CHANGES` (never on the viewer's own pull request), `APPROVE` (only when the verdict is approve, never on the viewer's own pull request), and "Don't post" (the draft stays in `$EVID`). A batch: one multiple-choice question per four pull requests, each option "owner/repo#n at <sha7> as <event>" with the verdict's event, ticked to post; a different event for one of them is asked for through the question's free-text answer. A yes given earlier, to anything else, never covers posting. When AskUserQuestion is not available (a headless run), give the handover's table first (`batch_report.py`, while the pre-approval holds), then ask the same question in text, with the options listed, and end the turn: the answer is the next message.
4. **Post what was chosen,** one review per pull request: rebuild each chosen payload with its chosen event, then `python3 <skill-dir>/scripts/post_reviews.py "$EVID" ...` with the chosen pull requests' evidence directories, in order. It posts one at a time under GitHub's limits for creating content (a batch of 15 was blocked after 10 in 34 seconds), waits out a rate limit as GitHub asks and tries again (retrying a review the user approved needs no new yes), never posts a review twice, and stops at any other refusal. Show its output with each review's link. For a refusal, show the error, fix that pull request's payload, and ask again before posting it; running the script again finds what is already posted. Never switch the event on your own.
5. **Never push** to a pull request's branch, and never merge, close, reopen, edit, mark ready, request or dismiss reviewers, or resolve threads. The review is the output.
