# Draft

1. **review.json.** Write `$EVID/review.json`: `{"pr": {"repo", "number", "url", "title", "author", "head", "mergeable"}, "verdict", "summary", "findings": [{"severity", "title", "body", "path", "line", "end_line", "side", "suggestion", "evidence", "verified", "proof", "requirement"}], "requirements": [{"id", "status", "evidence"}], "intent": {"sources": [...]}, "not_verified": [...]}`. Paths are relative to the repository root; lines are the candidate's (side RIGHT), or the baseline's for a removed line (side LEFT). The summary is three sentences at most: what the pull request does, whether it does it, and the one thing to fix first. A finding with nothing to suggest leaves `suggestion` out; a deletion is proposed in words (an empty suggestion block deletes lines on GitHub). No local paths, machine names or secrets anywhere in it.
   - `"verified": true` says you opened the finding's lines at the candidate and the claim held (a question or praise needs none). `"proof"` is what a blocking finding rests on: `check` (a check broken by the PR, with its log), `probe`, `reproduction` or `citation` (the lines, read, under static review); the finding's `evidence` names it. The poster reads these fields to decide whether the review may post by itself, so mark nothing verified that you did not check.
   - With a `reference.json` beside `review.json` (`reference.md`), `requirements` has one entry per line of it: `id` (`R1`...), `status` (`met`, `unmet`, `not applicable`, or `not verified` when you could not settle it) and the `evidence`. An unmet line is a blocking finding whose `requirement` is that id. `intent` names the sources' labels; with none, `{"sources": [], "note": "no independent spec: intent is the author's own description"}`.
2. **The review GitHub receives.** `python3 <skill-dir>/scripts/review_payload.py --diff "$EVID/pr.diff" --review "$EVID/review.json" --checks "$EVID/checks/checks.md" --event <the verdict's event> --viewer <login> --out "$EVID/payload.json" --preview "$EVID/review.md"` (without `--checks` under static review). It anchors each finding inside the diff (GitHub rejects the whole review when one comment misses) and moves the rest to the body under outside the diff, turns suggestions into suggestion blocks, ends the body with a one-line footer saying the review was drafted with Claude Code and whether checks ran, and refuses an event GitHub or the evidence does not allow (the author of a pull request can only comment on it; approve is refused with a blocking finding, a check broken by the PR or a merge conflict). With a `reference.json` it adds a Requirements section: each line's number, status and short title, never the reference's text or its path. The verdict's event is `REQUEST_CHANGES`, `APPROVE` or `COMMENT`; on the viewer's own pull request it is `COMMENT`.
