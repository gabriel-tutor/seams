# Post

Every review reaches GitHub through `python3 <skill-dir>/scripts/post_reviews.py`: `--auto` for a review that may post by itself, without it for one a person chose. Nothing else posts.

1. **Show the draft.** Every pull request's `review.md` in full: the body and each inline comment with its place. A review `evidence.py` found posted at this head is not asked about again; its link (`posted.json`) goes in the handover.
2. **Re-check the candidate** just before posting: `gh pr view <n> --repo <owner/repo> --json headRefOid`. A pull request that moved since the review is stale and is not posted: a head is reviewed again, twice at most in one request: pin and review the new head the same way, without asking; one that moves a third time is left to the user, with the drafts in `$EVID`.
3. **Post by itself what the code finds fully verified.** Unless the request says `draft only` (then step 4 asks about every review), run `post_reviews.py --auto "$EVID" ...` with every review's evidence directory, in order. The code reads the evidence on disk, not your say-so, and posts a review without a yes only when: the viewer can push to the repository; `checks.json` lists a check and none could not run or was flaky; nothing is under not verified; every finding but a question or praise is `verified` and every blocking one has a `proof`; every requirement line of the reference has a status, an unmet one a blocking finding; and an `APPROVE` has an independent reference with at least one line, none unmet. It prints `needs your yes: <review>: <why>` for any other and goes on to the next. A review it posts says in its footer that it was posted automatically and that no person read it first, and the pull request gets one label: `pr-review: approved`, `changes requested` or `commented` (its own prefix, created once; a label the repository uses is never touched, and one that cannot be applied is reported and never undoes the review). A review of the viewer's own pull request is only `COMMENT`.
4. **Ask about the rest, every time.** For each review that needs your yes, with AskUserQuestion, naming the pull request, the candidate and the event. A single review: "Post this review to owner/repo#n at <sha7> as <event>?", options: the verdict's event (recommended), `COMMENT`, `REQUEST_CHANGES` (never on the viewer's own pull request), `APPROVE` (only when the verdict is approve, never on the viewer's own pull request), and "Don't post" (the draft stays in `$EVID`). A batch: one multiple-choice question per four pull requests, each option "owner/repo#n at <sha7> as <event>" with the verdict's event, ticked to post; a different event for one of them is asked for through the question's free-text answer. A yes given earlier, to anything else, never covers posting. When AskUserQuestion is not available (a headless run), give the handover's table first, while the pre-approval holds (`batch_report.py` without `--close`: the batch stays open until the final handover), then ask the same question in text, with the options listed, and end the turn: the answer is the next message.
5. **Post what was chosen,** one review per pull request: rebuild each chosen payload with its chosen event, then `python3 <skill-dir>/scripts/post_reviews.py "$EVID" ...` (no `--auto`: a person chose) with the chosen pull requests' evidence directories, in order. It posts one at a time under GitHub's limits for creating content (a batch of 15 was blocked after 10 in 34 seconds), waits out a rate limit as GitHub asks and tries again (retrying a review the user approved needs no new yes), never posts a review twice, and stops at any other refusal. Show its output with each review's link. For a refusal, show the error, fix that pull request's payload, and ask again before posting it; running the script again finds what is already posted. Never switch the event on your own.
6. **After a batch's fan-out** this step runs in a later turn, outside the skill's pre-approval: Claude Code asks the user to allow `post_reviews.py` unless their own permission settings already do (`Bash(python3 *post_reviews.py *)`). Say so; until it is allowed, the reviews stay drafted in `$EVID`.
7. **Never push** to a pull request's branch from here, and never merge, close, reopen, edit, mark ready, request or dismiss reviewers, or resolve threads. The review is the output; pushing is the take-over's alone (`takeover.md`, on the user's yes).
