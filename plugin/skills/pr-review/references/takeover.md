# Take-over

For a pull request the review found not ready to merge, when the user answers yes to "Short on time? Take this PR over?": fix it so it can merge now, without waiting for the author. The user's yes starts the fixing; the push has a yes of its own. Merging stays the user's, always.

1. **Where the fixes may go.** Re-check the candidate (`gh pr view <n> --repo <owner/repo> --json headRefOid`): a head that moved since the review is reviewed again first (`post.md`, step 2). Gather the facts with `gh pr view <n> --repo <owner/repo> --json number,title,url,author,isCrossRepository,maintainerCanModify,headRefName,headRefOid,headRepository,headRepositoryOwner,baseRefName`, `gh repo view <owner/repo> --json viewerPermission`, `gh api users/<head repository owner> --jq .type` and `gh api users/<author> --jq .id`, and write them with the Write tool to `$EVID/takeover/facts.json` as `takeover.py target` documents (`python3 <skill-dir>/scripts/takeover.py target --facts "$EVID/takeover/facts.json"`; read its docstring with `--help`). Save its answer as `$EVID/takeover/target.json` and tell the user where the fixes go and why: `author-branch` (the author's branch, where GitHub lets the user push), `new-branch` (a new branch `takeover/<n>-<branch>` of the user's in the base repository, with a new pull request that names the author's) or `fork` (the user cannot push to the base repository: nothing is pushed; the fix stays in the worktree and the user decides about a fork).
2. **Fix in a worktree.** `git -c core.hooksPath=/dev/null -C <repo> worktree add --detach "$EVID/takeover/tree" <headRefOid>`, and a marker like the review's own, so Cleanup removes it. Fix only what the review's blocking and should-fix findings asked for, the smallest change that does it, a regression test first where the finding's proof was a probe (the probe in `$EVID/probes/` is the test). What the Gate's trust answer allows is what runs: for a pull request reviewed statically, ask the Gate's three questions again before running anything of it. Commit once, with the trailer `target.json` names (`Co-authored-by`, the author's noreply address) on every commit, so the author keeps credit. The fix goes on top of the author's commits: never a force push, never a rewrite of them.
3. **Prove it.** Run the checks again on the fixed tree, beside the baseline (`run_checks.py --base "$EVID/base" --head "$EVID/takeover/tree" --out "$EVID/takeover/checks" --base-from "$EVID/checks" ...`, as `checks.md` says, with the review's own commands: `--base-from` takes each baseline run the review believed, a pass or a failure a second run confirmed, instead of running it again on the same tree), and show the table beside the review's, with the diff in full (`git -C "$EVID/takeover/tree" diff <headRefOid>..HEAD`). A fix that leaves a check broken, or breaks another, is not offered: say so.
4. **Ask before pushing,** with AskUserQuestion, naming the repository, the branch, the mode and the commit: "Push <sha7> to <owner/repo>:<branch> (<mode>)?", options "Push (Recommended)" and "Don't push (the fix stays in `$EVID/takeover`)". Nothing is pushed without that yes.
5. **Push** with `python3 <skill-dir>/scripts/takeover.py push --target "$EVID/takeover/target.json" --worktree "$EVID/takeover/tree" --commit <sha> --repo <owner/repo> --branch <branch>`, the repository and branch written out from `target.json`. It is not pre-approved: Claude Code's own permission prompt shows the exact repository, branch and commit on the command line, and that is the yes it needs too (the script refuses a repository or branch that is not the file's). It pushes the commit, and the commits before it back to the pull request's head, and refuses when the commit is not the worktree's head, does not continue the pull request, adds nothing, lacks the author's trailer (unless the pull request is yours), is a new branch outside `takeover/`, or would need a force. For `new-branch`, open the pull request with `python3 <skill-dir>/scripts/takeover.py open --target "$EVID/takeover/target.json"` (not pre-approved either; it runs `gh pr create` itself, so the author's title never goes through a shell). A target whose mode is null has no author to credit: stop and tell the user. Say what was pushed and where, and that a re-review of the new head is the same command.

**Several at once.** When the user says yes to more than one pull request, the steps above run for each in parallel, and step 4 asks once for them all:

- **In this session first,** one pull request at a time: step 1 (the re-check, the facts, `target.json`) and step 2's worktree (git's locks would race), and, for a pull request reviewed statically, the Gate's three questions again, every one in a single round.
- **Then one subagent per take-over,** with the Agent tool (general-purpose, in the background), as many at once as there are check slots, the next as one finishes. Give it facts only: `$EVID`, its worktree, `target.json`, the trust answer, the checks list, the slot count and this skill's directory. Its instruction: read `<skill-dir>/references/takeover.md` and `references/checks.md`, carry out step 2's fix and step 3's proof for this one pull request, never ask the user anything, never push, and reply in one line with the fixed commit, or why there is none.
- **After the last one finishes:** each one's table and diff as step 3 says (a fix that leaves a check broken, or breaks another, is not offered), then step 4 once: one multiple-choice question per four take-overs, each option "Push <sha7> to <owner/repo>:<branch> (<mode>)", ticked to push; nothing unticked is pushed.
- **Push what was ticked in one Bash call,** step 5's `takeover.py push` once per take-over, joined with `;`, so Claude Code's single permission prompt shows every repository, branch and commit; then `takeover.py open` for each `new-branch` one, likewise in one call. Each push still refuses on its own anything step 5 names.
